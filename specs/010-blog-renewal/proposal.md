# SCLOG 리뉴얼 기획

## 현재 방향 — 2026-10-20

사용자 결정: “그냥 완전 블로그 느낌으로만 갈게 포트폴리오 안하고.”

- 사이트는 글을 탐색하고 읽는 블로그로 구성한다. 포트폴리오, 경력 전시, 대표 프로젝트·데모를 중심으로 한 구성을 제외한다.
- 자기 PR이라는 활동의 목적은 글에 담긴 관점과 경험으로 전달한다. 별도의 포트폴리오 동선을 전제하지 않는다.
- 홈은 블로그 이름과 글 목록을 중심으로 설계한다. 기존의 가로형 글 카드 선호를 바탕으로, 글 상세와 함께 다음 기획 대상으로 삼는다.
- 기존 글과 이미지를 보존한다. AI 기능은 계속 보류한다. 직접 제작·소스 공개 의향은 유지하되, 구현 보기를 대표 기능으로 삼지 않는다.
- 모션그래픽·타이포 포스터 시안은 과거 탐색 자료로 남긴다. 현재 블로그의 필수 메인 화면이나 채택된 디자인으로 취급하지 않는다.

현재 단계는 기획이다. 이 결정으로 실제 사이트나 기존 시안을 수정·삭제하거나 배포하지 않는다. 다음 작업은 **글 목록 중심 홈의 정보 밀도와 글 상세의 읽기 경험**을 정하는 것이다. 시각 기준은 루트 `DESIGN.md`에서 관리한다.

기존 글의 URL은 실제 적용 시 보존한다. 미리보기에서는 `article.html`로 연결한다. 시각 수치는 루트 `DESIGN.md`의 검토용 시안 항목에 기록했다.

## 홈 구도 초안 — 2026-10-22

블로그 중심 방향과 가로형 카드 선호를 바탕으로 한 검토용 구도다. 아직 화면 구현이나 최종 디자인 확정 단계는 아니다.

### 콘텐츠 기준

현재 저장소 `src/content/blog/`에는 글이 한 편 있다. 실제 제목·날짜·이미지로 홈을 구성하며, 빈 공간을 채우기 위한 가상 글이나 같은 글의 중복 노출은 만들지 않는다.

- 제목: 프로 개발자 2023일 후기
- 작성일: 2023.04.30
- 이미지: `/images/blog/pro-developer-2023-days/hero.png`
- 카드 요약 초안: “개발자로 일하며 배운 비즈니스와 팀의 이야기.” 기존 글 설명을 목록용으로 줄인 제안이며, 원본 콘텐츠는 변경하지 않는다.

### 배치와 읽기 순서

- 홈 자체를 전체 글 목록으로 사용한다. 블로그 이름 아래에 첫 글의 제목과 요약이 바로 보이도록 상단 여백을 잡는다.
- 카드는 기존 선호대로 데스크톱에서 왼쪽 썸네일, 오른쪽 제목 → 요약 → 날짜 순서로 배치한다. 제목을 가장 선명하게, 날짜는 보조 정보로 표시한다.
- 모바일에서는 썸네일 → 제목 → 요약 → 날짜 순으로 쌓는다. 썸네일 높이를 조절해 첫 카드의 제목이 첫 화면 안에 들어오도록 검토한다.
- 카드 전체를 하나의 글 링크로 취급한다. 이미지·제목·별도 읽기 버튼을 각각 중복된 클릭 지점으로 나누지 않는다. 썸네일이 없는 글은 이미지 자리를 비우지 않고 텍스트로 구성한다.
- 카드 사이에 충분한 간격을 두고, 글 수에 맞게 페이지가 자연스럽게 끝나도록 한다. 푸터를 화면 맨 아래로 밀기 위해 큰 빈 영역을 추가하지 않는다.

### 현재 콘텐츠에 맞춘 범위

글 한 편 기준에서는 검색·카테고리 탭·추천 글·인기 글·페이지네이션을 홈에 추가하지 않는 구도로 시작한다. 이는 기존 기능 삭제 결정이 아니라 새 홈의 초기 노출 제안이다. 글이 늘어나 탐색 필요가 생기면 검색과 분류를 검토한다. 기존 글 상세 주소는 유지한다.

다음 기획 대상은 **글 상세의 제목·메타 정보·본문 폭·이미지·코드 블록 배치**다.

## 1. 확정된 목적

블로그는 작성자를 알리고 채용, 협업·사업, 업계 인지도 기회로 연결하는 마케팅 수단이다. 사이트 자체가 개발 역량을 보여주어야 한다. 디자인 시스템부터 필요한 요소를 직접 만들고 소스를 공개하며, 사용 중인 기능에서 관련 소스로 이어져야 한다. 기존 글과 이미지는 보존한다.

직접 제작은 전체 로드맵의 원칙이다. 프레임워크·컴파일러·저장소·호스팅까지 직접 만드는지는 아직 정의되지 않았으며, 이 문서에서 임의로 제외하거나 교체 확정하지 않는다. 첫 실행 범위는 디자인 시스템과 실제 페이지에 집중한다.

권장: SCLOG를 직접 만든 웹 시스템이 실제로 운영되는 장소로 만들고, 방문자가 원하는 깊이까지 구현을 살펴보게 한다. 첫 화면은 완성된 제품의 인상을 주고, 상세 문서는 그 인상을 검증할 근거를 제공한다.

시각 방향 제안: 한국어 본문에 적합한 타이포그래피, 충분한 여백, 낮은 채도의 바탕에 한 가지 강조색, 상태 변화가 명확한 짧은 모션. 홈·대표 데모에서는 개성을 강조하고, 글 상세에서는 읽는 경험을 우선한다. 기존 코랄·폰트·레이아웃은 확정 요구가 아닌 재검토 대상이다.

## 4. 핵심 경험: 구현 보기

예: 테마 선택을 사용 → `구현 보기` 선택 → 테마 컴포넌트 설명 → 상태별 데모·검증 → 현재 배포 버전의 소스.

평소 화면에는 모든 요소의 기술 설명을 붙이지 않는다. 헤더나 푸터에서 구현 보기 진입점을 제공하고, 활성화했을 때 등록된 요소를 선택할 수 있게 한다. 첫 버전은 모든 DOM을 자동 분석하는 도구 대신 주요 요소의 명시적 연결로 시작한다.

키보드와 터치에서도 같은 문서로 갈 수 있도록 요소 목록을 함께 제공한다. 호버·단축키 전용 기능으로 만들지 않는다. 원래 버튼의 동작과 검사 선택 동작이 충돌하지 않도록 모드를 명확히 구분하고 쉽게 종료할 수 있게 한다.

개별 문서는 다섯 내용을 제공한다.

1. 실제 블로그에서 사용하는 동일 컴포넌트의 데모.
2. 해결한 문제, 설계 선택과 대안의 장단점.
3. 필요한 상태·입력 방식·테마별 동작.
4. 실제 수행한 테스트와 측정 조건·날짜.
5. 배포 커밋 기준 소스 링크, 최신 개발 코드 링크, 관련 글.

소스 연결은 파일 위치와 컴포넌트 ID를 명시적으로 관리한다. 배포 커밋 링크를 사용하면 방문자가 본 화면과 확인하는 코드가 어긋나는 일을 줄일 수 있다. 링크가 실제 파일을 가리키는지도 빌드에서 검증할 것을 제안한다.

| 2 | 구현 보기, 문서 템플릿, 소스 연결 | 주요 요소에서 데모·설계·배포 버전 소스까지 이동 |
| 3 | 홈·탐색·소개·검색 및 대표 인터랙션 | 방문자가 역량 확인 후 글·소스·연락으로 이동 |
| 4 | 콘텐츠 작성·미리보기·발행 시스템 | 실제 글 작성과 발행에 사용하고 내부 동작을 설명 |
| 5 | 분석·운영 도구, 빌드·배포 자동화의 자체 구현 범위 확장 | 실제 운영 데이터와 장애·복구 검증에 근거한 사례 공개 |

각 단계는 전체 범위를 줄이는 것이 아니라 공개 순서다. CMS와 운영 도구까지 다 끝나야 첫 공개를 할 수 있는 구조는 피한다. 기존 댓글 등 기능은 보존·대체·출시 시점 결정을 별도로 기록한다. 이 기획 단계에서 제거하지 않는다.

현재 저장소는 Astro·MDX를 사용하고 Storybook·Vitest 설정이 있다. 완성형 UI인 shadcn/Radix 의존과 자체 컴포넌트 작성 원칙의 관계는 구현 전 정리해야 한다. 자체 제작 원칙상 새 디자인 시스템의 스타일·상태·동작은 직접 설계·구현하는 방향을 제안한다. 기반 기술 교체는 이 문서에서 결정하지 않는다.

## 7. 첫 출시 제안

첫 결과물은 기존 글 한 편이 새 디자인 시스템으로 표시되고, 테마와 코드 블록의 구현 문서·소스까지 연결되는 작은 완성본이다. 이후 홈으로 확대한다. 처음부터 방대한 범용 컴포넌트 목록을 만들기보다 실제 화면에서 필요한 요소를 끝까지 만든다.

수용 기준:

1. 기존 글의 본문·이미지·URL을 보존하며 모바일과 데스크톱에서 읽을 수 있다.
2. 문서 데모와 운영 화면이 동일 구현을 사용한다.
3. 테마 변경과 구현 보기 동선을 키보드·터치로 완료할 수 있다.
4. 구현 설명에서 실제 배포된 버전의 소스에 도달하고 링크 검증을 통과한다.
5. 기능·접근성 검증 결과를 실행 환경과 함께 기록한다. 실행하지 않은 결과나 보장할 수 없는 수치를 표시하지 않는다.

자체 UI의 품질 근거로 [W3C APG](https://www.w3.org/WAI/ARIA/apg/patterns/)의 관련 패턴을 참고한다. [APG 주의사항](https://www.w3.org/WAI/ARIA/apg/practices/read-me-first/)은 ARIA role만 추가해도 키보드 동작이 생기는 것은 아니며 실제 브라우저·보조기술에서 검증해야 한다고 설명한다. 자체 구현의 범위에 이러한 동작과 검증도 포함한다.

## 8. 마케팅 효과 확인

제품 완성도와 마케팅 효과는 별개로 측정한다. 대표 데모 → 시스템 문서 → 소스 → 연락으로 이어지는 행동을 살펴보고 개선한다. 이벤트 수집이 없거나 적은 초기에는 실제 방문자 관찰과 피드백으로 확인한다. 클릭 증가를 곧바로 채용 성과로 해석하지 않는다.

첫 사용자 검토 질문은 “이 사이트를 만든 사람에게 어떤 일을 맡기고 싶은가?”로 제안한다. 답이 목표한 역량과 일치하는지 확인한다. 소스 공개 여부만큼 문제 정의·트레이드오프·유지보수성도 보이는지 점검한다.

## 9. 다음 결정

권장 결정: ‘사용하는 블로그에서 구현까지 탐색’ 콘셉트를 채택하고, 디자인 시스템·글 상세·구현 보기의 연결을 첫 기획 범위로 삼는다.

그다음 단계는 홈과 글 상세, 구현 문서의 화면 구성을 만드는 일이다. 전체 직접 구현의 기술적 하한(프레임워크·빌드 도구·호스팅 등)은 스택 결정 전에 구체적인 선택지로 별도 합의한다.
