# Research: 직접 만든 블로그를 통한 개발자 마케팅 사례

**Date**: 2026-09-30
**Status**: 기획 참고 자료. 구현 또는 스택 결정 아님.

## 조사 질문

디자인 시스템부터 블로그 구성 요소를 직접 만들고 공개할 때, 방문자가 실제 결과물을 경험하고 구현 근거까지 확인하게 만드는 패턴은 무엇인가?

아래 사실은 본인의 사이트·글·공개 저장소를 근거로 한다. 적용 제안은 조사자의 해석이며, 사례가 채용 성과를 보장한다는 뜻은 아니다. 페이지 구조와 텍스트를 확인했으며 실제 브라우저에서 시각·성능·접근성을 검증하지 않았다.

## 1. Emil Kowalski: 작은 구현 결과물을 독립적인 작품으로 공개

### 확인된 사실

- 개인 사이트에서 Sonner·Vaul 등의 프로젝트와 제작 과정을 설명하는 글을 함께 소개하며, GitHub로 연결한다. [개인 사이트](https://emilkowal.ski/)
- Sonner 저장소는 소스·테스트·MIT 라이선스를 공개하며, README에서 데모/문서와 제작 이유를 설명하는 글로 연결한다. [Sonner 저장소](https://github.com/emilkowalski/sonner)
- 본인은 UI 작업을 공개한 뒤 Compound의 연락과 채용을 경험했고, 지속적인 공개 활동 뒤 Vercel의 연락과 합류로 이어졌다고 설명한다. 이는 당사자의 경력 회고이며 독립적인 인과 검증은 아니다. [Animating in Public](https://emilkowal.ski/ui/animating-in-public)
- Vaul은 현재 README에 유지보수 중단을 명시한다. 공개한 결과물의 품질과 지속적인 유지보수는 별개의 문제임을 보여주는 사례다. [Vaul 저장소](https://github.com/emilkowalski/vaul)

### sclog에 적용할 패턴 — 해석

블로그를 한 번에 소개하는 것 외에, 검색·코드 블록·이미지 뷰어 등 완성한 요소마다 작은 공개 결과물을 만든다. 각 결과물은 `직접 사용 → 설계 설명 → 소스와 테스트`로 연결한다. npm 패키지 배포는 별도 결정이며 공개 소스와 동일시하지 않는다.

## 2. Josh W. Comeau: 사이트 자체와 글 속 데모가 역량의 증거

### 확인된 사실

- 본인은 블로그를 템플릿·UI 프레임워크·컴포넌트 라이브러리 없이 직접 디자인하고 만들었다고 설명한다. 동시에 애니메이션·아이콘 등에는 외부 도구를 사용한다고 밝힌다. 따라서 이 사례를 모든 의존성의 자체 구현으로 해석하면 안 된다. [Contact FAQ](https://www.joshwcomeau.com/contact/)
- 제작기에는 자체 재사용 `Demo` 컴포넌트와 제어 UI를 조합해 글 속 인터랙티브 예제를 만드는 방식, 문맥에 따라 조정되는 컴포넌트 스타일이 설명돼 있다. [How I Built My Blog](https://www.joshwcomeau.com/blog/how-i-built-my-blog-v2/)
- 사이트 전체는 명시적으로 closed-source이며, 프로덕션 소스맵을 통해 클라이언트 구현을 볼 수 있게 한다. 오픈소스 블로그 사례로 분류해서는 안 된다. [Contact FAQ](https://www.joshwcomeau.com/contact/)

### sclog에 적용할 패턴 — 해석

디자인 시스템 문서를 별도의 색상표에 그치게 하지 않고 실제 글과 화면에서 쓰는 컴포넌트로 구성한다. 같은 요소를 블로그 본문, 독립 데모, 소스 문서에서 확인하게 연결하면 결과물과 설명 사이의 불일치를 줄일 수 있다. 사용자는 공개 소스를 원하므로 Josh의 비공개 정책은 따르지 않는다.

## 3. Paco Coursey: 개인 사이트에서 공개 프로젝트와 사고방식으로 연결

### 확인된 사실

- 홈에 인터페이스 제작이라는 정체성, cmdk·Writer·Next Themes 프로젝트, 글, 연락처를 배치한다. cmdk 등 프로젝트 링크가 공개 저장소로 연결된다. [개인 사이트](https://paco.me/)
- cmdk 저장소는 컴포넌트 소스, 웹사이트, 테스트와 `ARCHITECTURE.md`를 함께 공개한다. 과거 `pacocoursey/cmdk` 주소는 현재 `dip/cmdk`로 연결된다. [cmdk 저장소](https://github.com/dip/cmdk)
- 2021년 리뉴얼 글은 애니메이션·기능을 계속 추가하기보다 성능·단순함·완성도·유지보수를 선택했다고 설명한다. 이는 당시 버전의 결정이며 현재 사이트 전체의 구현 방식으로 일반화하지 않는다. [Redesign 2021](https://paco.me/writing/redesign-2021)

### sclog에 적용할 패턴 — 해석

직접 구현한 범위는 넓어도 방문자가 처음 마주하는 화면은 단순하게 유지할 수 있다. 홈에서는 대표 결과물 몇 개를 바로 경험하게 하고, 기술 리더가 더 깊이 볼 때 문서·아키텍처·테스트로 이어지게 한다. 모든 내부 도구를 최상위 메뉴에 늘어놓을 필요는 없다.

## 역제안으로 연결할 결론 — 해석

1. **사이트는 실제 사용 공간이자 공개 구현의 입구로 설계한다.** 글을 읽는 과정에서 직접 만든 검색·타이포그래피·코드 블록 등을 경험한다.
2. **각 기능에 구현을 확인할 경로를 제공한다.** 관련 데모·설계 문서·정확한 소스 파일로 연결하며, 저장소 루트 링크만으로 끝내지 않는다.
3. **디자인 시스템은 실제 서비스와 같은 구현을 사용한다.** 문서용으로만 그럴듯한 컴포넌트를 따로 만들지 않는다.
4. **일부 대표 요소를 깊게 공개한다.** 미세 인터랙션, 키보드 동작, 모바일 사용, 성능 검증을 함께 보여주는 요소가 역량을 평가할 근거가 된다.
5. **전체 자체 제작과 전체 동시 개발을 분리한다.** 목표 범위를 유지하되 블로그에 필요한 흐름 단위로 완성·공개한다. 외부 사용자를 위한 패키지 지원 여부는 명시한다.

## 조사 한계

Rauno Freiberg와 Lee Robinson도 후보로 조사했으나 이번 웹 도구에서 본인 사이트의 핵심 페이지를 안정적으로 읽지 못했다. 2차 출처를 근거로 세부 동작이나 소스 공개 상태를 주장하지 않았으며 사례 비교에서 제외했다. Paco의 개인 사이트 전체 소스 공개 여부 역시 확인하지 않았고, 링크된 개별 프로젝트의 공개 상태만 기록했다.
